### 1.3 审计旗标处置（2026-10-08 复跑）

取证方法：临时脚本按 `LAYOUT_LABELS` 逐码 `computeLayout`，打印每码的
「两两压框 + 一级分支坐标序列」。下列每条都有实测数字，不是读代码猜的。

1. ~~几何测试 2/20~~ **已修**：新增「全码几何回归」段，码表从 `LAYOUT_LABELS` 自动展开，
   断言四件通用不变量（盒子齐 / 连线数 / 互不压框 / 包围盒自洽）+ 每族一条方向或镜像断言。
   layout.test.ts 49 例 → 175 例，全库 1079 → 1205 例。
   2026-10-08 再补两条（连线形状，见第 6 条）：layout.test.ts 189 例，全库 1219 例。
2. ~~emmx 往返测试在 CI 静默跳过~~ **已修**：真亿图夹具（345 KB，未跟踪、且是别人的作品）不该入库，
   但它一度是整份测试的唯一入口——夹具缺失时全文件 skip，CI 里 0/0，绿得毫无意义。
   处置：在夹具分支**之外**加一段合成夹具（`createDocument` 现造 5 主题文档），跑同一批核心承诺——
   往返幂等 / MainIdea 与双向子索引 / 陌生码 V=7 不被降级 / 本地专属码写回退值 6 /
   StyleMask 独立配色那一位 / 批注·超链接·标签 / 未识别标签（FutureTag）在正文重生成后仍在 /
   发号不撞已用 ID / 中文资源名与 thumbnail 按原字节带回 / 坏输入报中文错。
   核验过"任何环境都跑"：把夹具路径临时指到一个不存在的文件，这一段仍报 **25 例全过**（原先是 0/0）。
   有夹具时 emmx.test.ts 63 → 86 例，全库 1219 → 1242 例。
   两处写法上的坑记一笔：
   ① 读侧会补默认值（`platform=win`、`bold=false`、`props.background`、`maxShapeId`、`layout.rawCode`），
      factory 造的文档那几项是 `undefined`，所以等价断言比的是「第一次往返 vs 第二次往返」，
      不是「factory 文档 vs 解析结果」——前者才是"保存再保存不该变质"的承诺。
   ② `rawCode` 只在「该码映射出来的名字 == 页面当前的 code」时才原样带回
      （codec.ts 的 `layoutCodeOfPage`），合成页必须用 `balanced`（6）打底，
      否则 `logicRight` 的 8 会先把 7 顶掉。
3. ~~`treeLeft` 命名旗标~~ **确认为真错，并已定夺**：
   - 实测：`treeLeft` 与 `orgUp` 的坐标逐值完全相同（root=18,-17 / 一级分支 -83,-78 …），
     `treeRight` 与 `orgDown` 同样相同 —— 也就是**四个码只有两套几何**，
     而「左下」实际画出来是**向上**。
   - 判据用参考软件自己的措辞：`_research/extract/qm-cn.tsv:2520-2526` 与 `:2949-2955` 里
     Tree Map 有 Bottom Right / Bottom Left / Top Right / Top Left / Down / Up 六项，
     中文即 右下 / 左下 / 右上 / 左上 / 向下（对称）/ 向上（对称）。
     六个菜单项不可能是两套几何，所以「角向（四角）」与「对称」必须分家。
   - 处置：新增 `layoutTreeCorner`（逐级缩进、父站自己子树的角上）负责四角，
     原 `layoutTreeFamily`（居中摊开）改名给两对称；补 `treeUpRight` / `treeUpLeft` /
     `treeDownSym` / `treeUpSym` 四码。角向式的连线另走 `cornerPath`
     （竖线贴父列、横线进子框近侧缘），不再复用组织结构图那套折线。
   - 遗留：角向式的具体缩进量与画线样式是按「目录树」常识定的，**没有截图级证据**；
     拿到实机图样后若不同，只改 `layoutTreeCorner` 的列宽与 `cornerPath` 即可，码表与测试骨架不动。
4. **新发现（已修）：垂直时间线把一级分支摞回同一行**。`layoutSpine` 无论横竖主轴，
   交替/斜刺的偏移都写在 y 上，竖直主轴时正好抹掉了沿轴推进的 y。
   实测：分支A × 分支C 重叠 53x32。改为「推进坐标走主轴、交替偏移走垂直轴」，
   并把竖直主轴的子树展开函数从 `layoutVerticalTreeSubtree` 换成横向展开那一个
   （换完前者的唯一调用点消失，已删，连带删掉只它用的 `vGap`）。
   连线随之按层分向：一级分支竖着接、再往外的子分支横着接。
5. **新发现（已修）：组织结构图（上下双向）把分支压进中心主题**。`assignSubtreeY`
   在 depth=0 时只让开自身半高，等于从根的圆心起算。实测：中心主题 × 分支A 重叠 25x18、
   × 分支B 重叠 56x18。改为先让开「根半高 + 间距」。
6. **新发现（已修）：直角折线族里混着斜线段**。这条只能靠**装机目检**发现——坐标断言全过，
   因为盒子位置本来就对，错的是画线。真机截图上 树状图（向下对称）/组织结构图（上下双向）
   的分支线中间是一段斜线，与 `buildConnectors` 上方「树/组织结构图用直角折线」的注释不符；
   上行枝的连线还从中心主题**底边**出发，先穿回父框再折上去。
   根因：`elbowPath` 非竖直分支写的是「横 → 斜 → 竖」三段（`.replace` 拼出来的那条斜段），
   竖直分支写死「底出顶进」。处置：两个分支都改成纯轴对齐折线，进出边跟随子节点方向
   （`Math.sign(c.y - p.y)` / `Math.sign(c.x - p.x)`）；`treeDownSym`/`treeUpSym`/`orgUp`/`orgDown`/`orgBoth`
   归入竖直折线，`matrix` 走横向 Z。垂直时间线的二级分支顺带修好落点（原来进子框顶边，现在进近侧缘）。
   测试补两条：折线族每条连线斜段数 = 0（随码表自动展开，覆盖 12 码）、orgBoth 上/下行连线的起止 y
   必须落在父子框的相对边上。layout.test.ts 175 → 189 例，全库 1205 → 1219 例。
   同时确认：装机后 WebView2 里六个新码的 DOM 盒子坐标与 `computeLayout` 逐值相同，引擎与渲染没有第二套真相。

## A-01 [P0·正确性] 快捷键标签测试平台耦合，macOS 本机必挂 2 例

**现象**（`npm test` 实测）：21 文件 980 例，978 过 2 挂，全在 `tests/shortcut.test.ts`：

```
✗ 标签跟着改 — 实际 "⌘⌥F" ≠ 期望 "Ctrl+Alt+F"        （tests/shortcut.test.ts:61）
✗ Ctrl+Shift+S 的写法 — 实际 "⇧⌘S" ≠ 期望 "Ctrl+Shift+S"（tests/shortcut.test.ts:104）
```

**证据链**（逐环实测）：
1. `src/utils/shortcuts.ts:329` `shortcutLabel(cmd, mac = isMac())`、`:311` `chordLabel(chord, mac = isMac())`——
   缺省参数取运行环境判断。
2. `src/utils/shortcuts.ts:303` `isMac()`：无 navigator 的环境按 Windows 布局；
   **但 Node 21+ 自带全局 `navigator`**，本机 node v22.22.3 实测 `navigator.platform === "MacIntel"`，
   命中 `/mac|iphone|ipad/i` → mac 布局。
3. `tests/shortcut.test.ts:103` 的注释「node 里没有 mac 的 platform，这里只断言非 mac 那一路」
   ——写测试时的前提在 Node 21+ 已经不成立；断言却没显式传 `mac=false`，于是"想测哪一路"漂移成"node 在哪就测哪一路"。

**CI 为什么没拦**（desktop-build.yml 实测）：
- ubuntu job 跑 `npm test`：runner 的 `navigator.platform` 非 mac → isMac()=false → 两例按 Windows 布局断言 → 绿；
- `runs-on: macos-latest` job（yml :95）只跑 `cargo test` + `build-desktop`，**不跑前端测试**。

净效果：**CI 全绿、mac 开发机红**——恰恰漏掉了 mac 这一路的回归。

**影响**：mac 上任何人对 shortcuts 相关代码跑本地测试都会先吃 2 红，污染"红=我改坏了"的信号；且 mac 布局本身零测试覆盖。

**修复方向**（按测试作者本意最小修）：`:61` 改 `shortcutLabel("search", false)`、`:104` 改 `chordLabel("ctrl+shift+s", false)`，
同时把 `:103` 注释改为"显式传 false 锁非 mac 布局（Node 21+ 有全局 navigator，不传会跟宿主平台走）"。
可选加固：再补两行 `mac=true` 断言（`⌘⌥F` / `⇧⌘S`），让两路布局都有锁。→ T-0-1

## A-03 [P0·CI] .npmrc 把 registry 钉死在 npmmirror，拖累 GitHub Actions

**证据**：根目录 `.npmrc` 内容实测只有一行 `registry=https://registry.npmmirror.com`；
desktop-build.yml 的所有 `npm ci` 步骤无 registry 覆盖。GitHub 海外 runner 走 npmmirror
（国内 CDN 面向国内优化的镜像）慢且偶发失败；同族其余仓没有这枚 pin。

**影响**：CI 时长与稳定性受损；本地开发者倒确实受益于镜像。

**修复方向**：保留本地 `.npmrc`，在 workflow 的 job 级加 env
`NPM_CONFIG_REGISTRY: https://registry.npmjs.org`（npm 配置优先级 env > project .npmrc，实测口径，
见 npm 文档 config 优先级；验收时以一次真实 CI 运行为准）。→ T-0-3

## A-04 [P0·发布] 从未发布：无任何 v* tag

**证据**：`git ls-remote --tags origin`（2026-10-08）→ 空；`scripts/release.sh` 头部注释与
desktop-build.yml（push tags v* 触发）齐备；三处版本载体（package.json / Cargo.toml / tauri.conf.json）一致 0.1.0。

**影响**：desktop-build.yml 的构建/签名链路从未被真实验证过；"能发"目前只是静态推断。

核对计划 → 用户点头 → `scripts/release.sh`（其内部 commit + tag + push 会触发 CI）→
Actions 产物（dmg/tar.gz/msi）人工验收。→ T-0-4（**对外不可逆，须用户批准**）

## A-08 [P1·审计] .emmx 已注册文件关联，打开链路疑似缺失（先复现再立项）

**证据**：`tauri.conf.json` 已注册 `.emmx` 文件关联（打包层配好了）；
但 `src/` 与 `src-tauri/src/` 实测 grep 不到任何文件打开处理
（`onOpenFile` / `fileOpen` / `RunEvent::Opened` / single-instance 插件均零命中）。

**影响**（推断，**未复现**）：双击 .emmx 或拖到 Dock 图标的行为未定义——可能无响应或起第二个实例。
注意 Tauri 2 的文件关联事件链路有版本细节，且 dev 与打包形态行为不同。

**修复方向**：**先实测复现**（打包形态双击/拖拽/`open xxx.emmx` 三种进路各试一次，记录行为），
确认缺失后再立项：单实例插件 + `RunEvent::Opened` → docStore 载入。→ T-1-4

> **【2026-10-08 修正】本条结论错误：打开链路完整存在且实测可用。**
> 复测（打包形态，`open /tmp/mind_open_test.emmx`）：单一实例接管（进程数 1），
> `~/.z-mind/logs/` 出现 `[open] 待打开路径交给前端： …mind_open_test.emmx`，
> `~/.z-mind/recent.json` 同步记录该路径——文件确被载入。
> 实际链路：`src-tauri/src/openfile.rs`（Pending 队列 + `open_take_pending`）
> ← `lib.rs` 的 `RunEvent::Opened`（macOS）/ `seed_from_args`（Win/Linux argv）
> → 前端 `App.tsx` 启动 take + `listen("open-path")` → `docStore.openPath`。
> 单实例靠 macOS 系统行为（二次 `open` 只回调 Opened，不起新进程），不装 single-instance 插件是 `openfile.rs` 头注里的明示设计决策。
> **误判根因**：grep 关键词（`onOpenFile`/`fileOpen`/single-instance）与真实命名不匹配，
> 且配置目录量错位置（真实为 `~/.z-mind`，非 `~/Library/Application Support/…`）。
> T-1-4 的交付相应改为：本修正 + 07 台账记录，不再立项开发。
